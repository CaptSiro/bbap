\section{System Architecture}\label{sec:system-architecture}
This section describes the challenges encountered during implementation of proposed design and techniques used to solve them.
The design expects full independence between system's components, in practice, some coupling emerges due to accessing shared
resources, execution order, communication, and reuse of code sections.

The architecture follows a hybrid approach combining:
\begin{itemize}
    \item Centralized data access through shared database connections.
    \item Globally accessible Request and Response objects.
    \item Interface-driven communication between components.
    \item Developer constants are defined in respective classes serving as static key-value look-up tables.
    \item Tooling for performing AI-Generation task are implemented as a part of the system.
\end{itemize}

This approach provides easily accessible datasets, that are needed in all parts of the system.

\subsection{Data Flow}\label{subsec:architecture-data-flow}
The design suggests a clean pipeline, but the actual execution model includes additional complexity:

\begin{itemize}
    \item Dependencies between components.
    \item Shared mutable and immutable states.
    \item Alternative execution paths based on runtime context.
    \item Configuration scattered over various number of media such as: .env file, immutable constants, and keys referencing database records.
\end{itemize}

These factors make the system execution convoluted compared to the idealized pipeline model.

\subsection{Architectural Trade-offs}\label{subsec:architectural-tradeoffs}
Multiple trade-offs were encountered while implementing every component:

\begin{itemize}
    \item Simplicity vs.\ Flexibility
    \item Abstraction vs.\ Performance
    \item Automation vs.\ Control
\end{itemize}

In practice, the implementation favors simplicity over flexibility, abstraction over performance, and control over automation.
This architectural decision limits the architectural flexibility in certain areas.

For example, the prototype currently supports only the OpenAI client to reduce complexity.
Similarly, it uses a custom HTTP route compiler to provide higher abstraction.
Finally, the database schema is initialized through SQL scripts rather than initializing it from model descriptions
for finer-grained control.

\subsection{Summary}\label{subsec:architecture-summary}
The system architecture exposes the complexity hidden behind the high-level design.
While the design goals emphasize simplicity, modularity, and extensibility, the implementation reveals constraints
imposed by abstractions, dependencies, complex configuration, and numerous edge cases.

The resulting architecture is a compromise between idealized design and practicality.
The prototype nature enables this kind of implementation and systems such as administration dashboard, configuration, routing, and testing
are going to be the first candidates for refactoring to get closer to the ideal implementation.

Implementation of all core functionalities fulfills the NFR5.
