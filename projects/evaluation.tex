\subsection{Testing the scenarios}\label{subsec:testing-the-scenarios}
This section outlines the results of implementing the scenarios.
The framework testing areas include CMS features, AI-Generation of content, and several development metrics.



\subsubsection{CMS Components}\label{subsubsec:cms-components}
\paragraph{Special Roles}
The system is based on a role-based access control model, which enables the administrators to create users
and assign them to groups.
Users inherit privileges from the groups they are part of.
The framework defines several special groups as a part of initial configuration.
For example, the Admin group grants implicit access to the administration dashboard.
Even if a user belongs to a group,
that grants the Page editing privilege,
without assigning the Admin group the user cannot log in to administration dashboard.

The system lacks proper descriptions for these special groups, and requires implicit understanding of the special groups.

\paragraph{File System Usability Concerns}
File management in the administration dashboard is functional but usability is suboptimal.
Currently, file upload is limited to drag-and-drop interaction within a designated area, which is hidden until
the user drags files over it.
This approach works for devices with a mouse pointer, but it might not function properly for devices with touch input methods.
The latter case was not tested, because touchscreen computer-like device was not available during development and testing.

Currently, uploaded files display file type icon, filename with extension, and size.
As a result, this makes it difficult to find files that are recognisable by their content.
For example, images are generally easier to identify via previews, which is not the case for current file listing.

To summarize, the File System implements basic functionality to upload file, create directory,
delete File System file or directory, and select file from listing, but requires implicit knowledge of the system,
assumes the use of specific device, and expects the user to remember files by name.

\paragraph{Missing Navigation Controls}
When navigating the administration dashboard the user must either use the menu on the left or rely on browser history navigation.
The menu includes initial pages sorted into categories and browser history provides linear navigation.
As a result, navigating within the page context may be suboptimal.
For example, currently, there is no direct navigation option to access parent page from property editor,
used to manage page template, status, and SEO\@.
The editor's title displays parent's title instead of the page's title that is being edited, which may confuse the users
if multiple property editors are opened from the same page parent.

\paragraph{Missing Progress Updates}
When an action that may take over a few seconds is performed, the system displays static modal window with the action title
and prevents the user from interacting with the website.
For example, when a file is being uploaded, the progress bar should be implemented to enable the user to infer
estimated upload time, or when multi-stage AI-Generation is performed, the system should display expected stages
and indicate when stage is completed with the completion status.

\paragraph{Page Structure Generation}
The generated structures are usable but a few pages need to be removed for each project.
For example, sometimes the Home page needs to be removed because it is implemented via the Home component.
A few times the AI generated the whole structure with Home being the parent.
Due to the system limitation not allowing transferring parent-child relation to other pages the whole structure
has to be deleted and regenerated.

In the content-driven scenario, the generated structure was ready to use and only blog articles had to be filled in manually.

\paragraph{Article Generation}
The generated output matched the desired content but the Markdown formatting had to be manually adjusted.
This is due to the use of a custom-made Markdown compiler, where some AI-Generated formatting choices
lead to undefined results.

\paragraph{Static Page Generation}
The static contact pages are generated using AI with simple prompt without styling guides
and detailed description of each scenario.
Combined with the use of a smaller model, this led to lower-quality results with mismatched theme styling
and incorrect typography.

\paragraph{Page Component Generation}
The page content generation is used to generate static table for corporate scenario.
With detailed prompt the output is visually presentable but not directly usable in production.
The issue is that generated components cannot expose editable properties or content to the editor.
If the user wants to edit the content, the change must be explicitly stated in the prompt rather than editing the output directly.

This makes the feature well-suited for drafting components in natural language and handing the output to the development team
to implement fully functional component.

\paragraph{Documentation Generation}
The AI-Generated documentation outlines source files and lists defined methods within each file.
The introduction is concise, the same applies to the method descriptions.
Due to the probabilistic nature of LLMs, the generated output varies in correctness, which is problematic in fact-driven environment,
such as technical documentation.
Additionally, the output is in Markdown format and inherits the same problems with formatting as Article Generation.

This means that for each documentation page the project maintainer needs to verify the correctness of the generated file,
and fix formatting before it can be declared production ready.
The issue is that the framework uses on-demand documentation generation,
which may expose users to incorrect and visually broken technical documentation.

This design decision introduces a trade-off between accessibility and reliability of the documentation.

All scenarios must implement custom homepage which counts as one manual intervention.
The personal scenario also includes extension-specific features:

\begin{itemize}
    \item Custom HTTP endpoints
    \item Extension component
    \item Freeform widget editor
    \item Static images
    \item Extension metadata

\paragraph{Time to Publishable Draft}
Measured from the initial commit to the final commit related to deployment.
Time spent bug fixing and updating the framework are excluded from the measurement.

The homepage is an exception because it requires meta description to be added manually by editing the Home component.



\subsubsection{Usability Evaluation}
This section explains what method is used to evaluate framework's usability.
A small-scale usability study is performed on five participants who finished the whole study.

The participants are asked to pick one of the outlined scenario and try to reimplement it, the respondent's choice is not tracked.
After finishing the scenario, all the respondents fill out the System Usability Scale proposed by John Brooke in 1986.
The standard version of SUS contains five positively worded and five negatively worded questions.
The answer is represented by five-point scale from one (\("\)Strongly Disagree\("\)) to five (\("\)Strongly Agree\("\)).
To evaluate the total SUS score per respondent the following formula was used~\parencite{lewis_sus}.

\[
    \mathrm{SUS} =
        2.5 \times
        \left(
            \sum_{i \in P}(x_i - 1)
            +
            \sum_{i \in N}(5 - x_i)
        \right)
\]

where \(P\) represents responses to positively worded questions and \(N\) represents responses to negatively worded questions.

The calculated SUS scores are shown in Table~\ref{tab:sus-results}.

The mean SUS score of the prototype usability study is 70, marked by red dot on scales~\ref{fig:sus-scales}.
The calculated mean SUS score is converted into grade scale and acceptance levels by thresholds
and mean scores above 70 are considered as acceptable~\parencite{setemen_sus}.

Three participants rated the system positively reaching the SUS score over 75, which indicates that the framework was easy
to learn or the framework used User Interfaces similar to other applications, such that the user could harness the knowledge.
One participant evaluated the framework with a score of 60, which indicates some friction while using the system.
However, one participant rated the system's usability negatively, reaching below the threshold of 50,
and classifying the usability as Not Acceptable.
The overall mean score is 70, which makes it barely acceptable.

This result suggests that certain groups of users may struggle with onboarding and navigating the system.
The individual scores indicates that usability of the system may depend on technical background and expectations of the user.
This observation is relevant because the target audience for the framework consists primarily
of users with technical backgrounds and developers,
and the framework's User Interface assumes a baseline in technical knowledge.

The usability evaluation has several limitations, that is sample size, selected user group, actions performed, and time spent with the framework.
The number of participants is very small, which reduces the statistical meaning of the results.
The participants are not selected from a broad user population.
The study asks the participants to recreate a scenario which includes development tasks as well as administrative tasks.
This decision limits users who are available to perform the study and evaluate the framework.
The respondents are asked to evaluate their initial interaction with the framework rather than long-term usage.

Future work should include larger sample size, splitting the tasks, and introduce feedback questions to identify the problematic areas of the framework.
