\section{Implementation Specifics of Scenarios}\label{sec:implementation-specifics-of-scenarios}
This section describes scenario-specific implementation details built on top of the framework.

\subsection{Corporate}\label{subsec:corporate}
The goal is to implement website for a software agency, that advertise their services, projects, and blog articles
using the CMS features.

Based on the goal, the following scenario-specific requirements are identified.

\begin{enumerate}
    \item Creation of websites presenting company services, projects, and blog articles using built-in CMS\@.
    \item Creation of a custom-made homepage.
    \item Integration of custom JavaScript files into existing components.
    \item Modification of existing component templates without requiring changes to the framework core code.
    \item Deployment of a basic corporate website through initial installation of the framework.
    \item Support for e-commerce functionality (not implemented).
\end{enumerate}

The Home component directory provided by the framework does not include JavaScript file,
but the design of the project's homepage requires extra JavaScript functionality and thus home.js is created
and the functionality is implemented.
The template is edited to import the script file using SideLoader's Javascript::import() method and the homepage layout
is designed and implemented.

The framework currently does not support e-commerce features, which limits the usefulness in corporate environment.
However, simple corporate requirements can be met with initial installment of the framework.

\subsection{Content-Driven}\label{subsec:contentDriven}
The goal is to implement website for the administrators to share a curated repository of recipes and cooking tips
using article templates and role-based privilege systems.

Based on the goal, the following scenario-specific requirements are identified.

\begin{enumerate}
    \item Support article management functionality, including creation, editing, deletion, and listing of articles.
    \item Allow the homepage to dynamically display the most recently updated articles.
    \item Configuration of homepage content, such as setting the number of featured articles listed.
    \item Support role-based access control for content management (this requirement satisfies UC7).
    \item Creation of user groups with defined privileges (e.g., Editor role).
    \item Support assignment of users to defined groups.
    \item Provide a system for storing configuration values editable by administrators.
    \item Support multi-author collaboration workflows (e.g., draft, review, publish states).
    \item Support logging of content modifications (not implemented).
    \item Provide categorizing articles and retrieving articles by category (not implemented).
    \item Support public content publishing (not implemented due to closed system design).
\end{enumerate}

The homepage needs to be updated to render last edited articles and list category pages.
The framework includes all the core functionalities needed to implement the behavior.
The following functions are implemented for the Home component to be accessible in the template.

\begin{verbatim}
    public function getCategoryPage(): ?Page {
        // Get from admin settings category parent page id
        $pageId = Setting::fromName(
            'savora:homepage-categories-page-id',
            true,
            1,
            [PROPERTY_EDITABLE => true]
        )->toInt();

        return Page::fromId($pageId);
    }

    public function getFeaturedPages(): array {
        // Get from admin settings how many articles to show
        $limit = Setting::fromName(
            'savora:homepage-featured-pages-count',
            true,
            3,
            [PROPERTY_EDITABLE => true]
        )->toInt();

        return Page::lastUpdated(limit: $limit);
    }
\end{verbatim}

With all needed backend features completed the template can be edited with custom homepage design.

In the administration dashboard, the user group Editor is created and privileges for content management are granted.
The group contains only one test user with the tag \("fizz"\),
which is a system-wide unique identifier used for authentication, and password \("fizzbuzz"\).

The framework currently supports only closed systems, in which the administrators create users who can manage the content.
This decision introduces a trade-off: it simplifies the implementation of content-driven systems, but reduces flexibility.

\subsection{Personal}\label{subsec:personal}
The goal is to create a Chrome extension which shows static image as background and displays widgets editable with built-in editor.

Based on the goal, the following scenario-specific requirements are identified.

\begin{enumerate}
    \item Binding of web pages to specific (external) URLs.
    \item Provide utilities for loading static assets (e.g., images, scripts) to client.
    \item Provide a system for storing configuration values editable by administrators.
    \item Integration for custom backend endpoints.
    \item Provide basic JavaScript utilities for building custom frontend behaviors.
    \item Support extending the frontend through custom JavaScript files without modifying core framework code.
    \item Provide a built-in visual widget editor capable of creating general UIs not limited to article style pages (not implemented).
    \item Provide built-in caching for external resources to reduce online dependency (not implemented).
    \item Provide abstraction for browser-extension specific integration (not implemented).
    \item Support automatic detection and synchronization of native file system and framework's file system (not implemented).
\end{enumerate}

To achieve this goal, the core of the extension is interactive webpage.
This enables live updates for the extension using HTML iframe element to load it, and up-to-date demonstration.
This architectural design introduces a trade-off: the extension requires a stable internet connection because the interface is remotely hosted.
However, after loading the interface, all content is generated from configuration stored directly in the user's browser.

The extension content page is part of the Action and View framework's systems, which enables direct binding to URL path.

\begin{verbatim}
    // index.php
    // Frame is the extension content page
    // Bound to protocol://domain/extension
    $router->use('/extension', new Frame());
\end{verbatim}

Fulfilling the requirement satisfies the UC3.

The page can be added to pages in administration as external page using fully qualified URL\@.

The freeform widget editor needs to be implemented by hand.
Support for custom editor is currently limited, still the framework provides general tools.
This includes, but it is not limited to:
asset loading, general JavaScript utilities, forms, and inspector controls from webpage content widget editor.

The scenario implements serving images from selected server directories as an extra feature.
To complete it, the web settings in administration dashboard are used and custom endpoint with following workflow is implemented:

\begin{enumerate}
    \item Get background paths defined in web settings
    \item Compute file difference in defined directories from last request
    \item Update internal files listing if any of the directories have been updated
    \item Select random image from internal files listing
    \item Send access URL to the selected image
\end{enumerate}

On extension startup, the endpoint is called and if URL is returned, the image is used as a background image.
To manage directories, the administrator must edit the appropriate web setting.
Multiple directories are supported by using the \(;\) (semicolon) directory delimiter.

The personal scenario demonstrates that the framework can be extended beyond traditional CMS-based applications.
Although interactive elements require manual implementation.
